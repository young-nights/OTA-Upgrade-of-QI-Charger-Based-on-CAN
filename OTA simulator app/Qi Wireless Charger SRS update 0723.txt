------------------------------------------------------------------------
一、Qi 充电器协议的更新内容
------------------------------------------------------------------------
以下是相较于此前交付版本的更新，请用随附的版本替换贵方现有的副本。


  • 软件版本 DID 变更：0xF189 → 0xF195。
    - 读取软件版本请使用：22 F1 95（肯定响应：62 F1 95 ...）。


  • SecurityAccess（0x27）与安全启动签名由 Ed25519 迁移为 ECDSA P-256
    （FIPS 186-4 / NIST secp256r1）：
    - 挑战 seed 先用 SHA-256 哈希，再进行签名。
    - 签名为原始 R‖S，固定 64 字节（IEEE P1363 格式，非 ASN.1 DER）。
    - 公钥为 65 字节非压缩 SEC1 点（0x04 ‖ X ‖ Y）；私钥为 32 字节标量。
    - Qi 模块需预置 CCU/测试端公钥并校验返回的签名；不匹配时返回 NRC 0x35
      （Invalid Key，无效密钥）。


  • ISO 14229-1 TransferData 对齐（请据此实现）：
    - 每次 TransferData 的可用负载 = maxNumberOfBlockLength − 2（RequestDownload
      响应中的长度包含了 0x36 SID + 块序号计数器）。
    - 块序号计数器回绕方式为 0xFF → 0x00 → 0x01（即 (n + 1) & 0xFF）。


  • 说明：普通（非 OTA）UDS 报文 —— 会话控制、DID 读写 —— 仍为明文，未做改动。
    仅 SecurityAccess / 安全启动使用 ECDSA P-256。


完整细节见随附文档：
  - qi_charger/docs/qi_charger_srs.md              （Qi 充电器 SRS v1.1）
  - common/docs/common_can_protocol_spec.md        （通用 CAN/UDS/ISO-TP 协议，REF-1，v1.1）


CAN 配置（未变）：Classical CAN 2.0B，250 kbps，29 位扩展 ID。
  - UDS 请求（CCU → Qi）：  0x18DA0D03
  - UDS 响应（Qi → CCU）：  0x18DA030D

二、上位机模拟器的使用方法
------------------------------------------------------------------------
模拟器充当 CCU（UDS 客户端，地址 0x03），针对贵方的 Qi 充电器模块（UDS 服务端，
地址 0x0D）驱动完整的 OTA 流程。它是一组 Python 源文件，请先安装运行环境与依赖库。


环境准备：
  a. 需要 Python 3.8 及以上版本。
  b. 安装依赖：   pip3 install -r requirements.txt
     （python-can、can-isotp、cryptography，以及贵方 CAN 适配器对应的驱动 ——
      例如 CANalyst-II 需 canalystii + pyusb；socketcan 无需额外驱动。）
  c. 总线接线：250 kbps，两端各接 120 Ω 终端电阻，并保证共地。
  d. 请在软件包根目录下运行所有命令，以便 common/ 与 qi_charger/ 包能正确导入。


先做离线加密自检（无需 CAN 硬件）：
     cd qi_charger/simulator/ecdsa-p256-keys
     python3 test_ecdsa_crypto.py     # 验证签名/验签及 0x27 流程
     python3 generate_keypair.py      # 生成测试密钥对（私钥 + 公钥）


  → 请将生成的【公钥】预置到贵方 Qi 模块中。上位机使用【私钥】签名；双方必须来自
    同一密钥对，否则 0x27 会以 NRC 0x35 失败。
    （注意：ZIP 内不含任何密钥对，需贵方自行生成测试密钥对。）


运行 OTA（以 CANalyst-II 为例）：
     cd qi_charger/simulator
     # 第一阶段 —— 简单安全版客户端：
     python3 qi_upgrade_client.py \
         --bustype canalystii --channel 0 --device 0 --bitrate 250000 \
         --firmware /path/to/qi_app.bin --type app --verbose


     # 第二阶段 —— ECDSA P-256 客户端：
     python3 qi_upgrade_client_ecdsa.py \
         --bustype canalystii --channel 0 --device 0 --bitrate 250000 \
         --keypair ecdsa-p256-keys/qi_ecdsa_p256_keypair.bin \
         --firmware /path/to/qi_app.bin --type app --verbose


两个客户端驱动的 OTA 流程：
     0x10 0x02（编程会话）→ 0x27（SecurityAccess）→ 0x2E 0x2010（选择固件类型）
     → 0x31 0x01 0xFF00（擦除）→ 0x34（RequestDownload）→ 0x36（TransferData）
     → 0x37（RequestTransferExit）→ 0x11（CCUReset）→ 0x22 0xF195（校验版本）。


软件包内的 README.md 与 qi_charger/simulator/README.md 提供了完整的参数说明和分步指引。


------------------------------------------------------------------------
三、建议的开发顺序
------------------------------------------------------------------------
两个客户端【除 SecurityAccess（0x27）步骤外完全一致】。我们强烈建议采用两阶段方式：


  第一阶段 —— 用【简单版】客户端（qi_upgrade_client.py）打通 OTA 主干流程。
    先在模块上实现简单的 seed+key 安全访问（key = seed + 0x5555），把整个传输与 OTA
    流程跑通：ISO-TP 分帧、会话控制、固件类型选择、擦除、RequestDownload、TransferData
    块序号处理、复位以及版本回读。这样可以把传输/流程问题与加密问题分开定位。


  第二阶段 —— 切换到 ECDSA P-256，并用 qi_upgrade_client_ecdsa.py 验证。
    主干流程稳定后，仅将模块的 0x27 步骤改为 ECDSA P-256 验签。由于其他环节不变，调试
    可聚焦在加密部分。


重要提示：简单的 seed+0x5555 算法【仅用于开发脚手架】。量产固件的 SecurityAccess 必须
按 SRS v1.1 §2.3 使用 ECDSA P-256；发布前请务必关闭或移除简单模式。


由于 Qi 充电器的 UDS OTA 在贵方是全新实现，从简单版客户端入手能最快跑通端到端流程。


如在开发或联调过程中有任何疑问，请随时与我们联系。
