### 第 4 节：CAN 物理与数据链路层

#### ✅ 4.1 CAN 2.0B Classical CAN

- **规范条款**: CAN 标准应为 CAN 2.0B，Classical CAN
- **代码位置**: `can_driver.c` → `can_driver_init()` → `can_mode_set(CAN1, CAN_MODE_COMMUNICATE)`
- **当前实现**: AT32F426 CAN 控制器配置为正常通信模式，发送/接收均使用 `CAN_ID_EXTENDED` 和 `CAN_FRAME_DATA`
- **结论**: ✅ 合规

#### ✅ 4.2 波特率 250 kbps

- **规范条款**: 波特率应为 250 kbps
- **代码位置**: `can_driver.c` 第 50-54 行（位时序常量定义）
- **当前实现**: APB1 = 180 MHz, 分频 10 → CAN 时钟 18 MHz, Tq = 1+54+17 = 72, 18MHz/72 = 250 kbps
- **结论**: ✅ 合规

#### ✅ 4.3 29 位扩展帧

- **规范条款**: 使用 29 位扩展帧
- **代码位置**: `can_driver.c` → `can_driver_send()` 中 `tx_buf.id_type = CAN_ID_EXTENDED`
- **当前实现**: 发送和接收均配置为扩展帧模式，滤波器也设置为 `CAN_ID_EXTENDED`
- **结论**: ✅ 合规

#### ✅ 4.4 最大 DLC 8 字节

- **规范条款**: 最大 DLC 为 8 字节
- **代码位置**: `can_driver.h` → `#define CAN_DRIVER_MAX_DATA_LEN 8U`
- **当前实现**: 发送函数中 `len > CAN_DRIVER_MAX_DATA_LEN` 时返回 -1
- **结论**: ✅ 合规

#### ✅ 4.5 小端序

- **规范条款**: 多字节载荷字段采用小端序
- **代码位置**: 全局 — ARM Cortex-M 天然小端序
- **当前实现**: AT32F426 基于 ARM Cortex-M4，原生小端序。ISO-TP 中的 12 位 FF 长度字段使用位移操作处理（`isotp.c` FF 处理），与小端序一致
- **结论**: ✅ 合规（依赖硬件平台特性）

### 第 5 节：诊断 CAN 标识符

#### ✅ 5.1 CAN ID 格式 0x18DA{TA}{SA}

- **规范条款**: UDS 诊断消息使用 J1939 风格 PDU1 寻址
- **代码位置**: `can_driver.h` 第 56-57 行, `can_protocol.h` 第 55-56 行
- **当前实现**: `CAN_ID_UDS_REQUEST = 0x18DA0D03`, `CAN_ID_UDS_RESPONSE = 0x18DA030D`，符合 0x18DA{TA}{SA} 格式
- **结论**: ✅ 合规

#### ✅ 5.2 CCU→外设: 0x18DAPA03

- **规范条款**: CCU 到外设的诊断请求 ID
- **代码位置**: `can_driver.h` → `CAN_ID_UDS_REQUEST = 0x18DA0D03U`（PA = 0x0D，Qi 充电器地址）
- **当前实现**: TA=0x0D（外设地址），SA=0x03（CCU 地址），符合规范
- **结论**: ✅ 合规

#### ✅ 5.3 外设→CCU: 0x18DA03PA

- **规范条款**: 外设到 CCU 的诊断响应 ID
- **代码位置**: `can_driver.h` → `CAN_ID_UDS_RESPONSE = 0x18DA030DU`
- **当前实现**: TA=0x03（CCU 地址），SA=0x0D（外设地址），符合规范
- **结论**: ✅ 合规

#### ✅ 5.4 仅接受 N_TA 匹配自身地址的请求

- **规范条款**: 外设应仅接受寻址到自身地址的请求
- **代码位置**: `can_protocol.c` → `can_protocol_rx_handler()` 第 176 行
- **当前实现**: `if (id != CAN_PROTO_UDS_REQUEST) { return; }`，仅处理目标地址为 0x0D 的请求
- **结论**: ✅ 合规

### 第 6 节：ISO-TP 传输层

#### ✅ 6.1 单帧载荷 0-7 字节

- **规范条款**: 单帧载荷 0 至 7 字节
- **代码位置**: `isotp.c` → `ISOTP_PCI_TYPE_SF` 分支
- **当前实现**: SF_DL 从 PCI 低 4 位提取，验证 `sf_dl > 0 && sf_dl <= len - 1`，支持 1-7 字节载荷
- **结论**: ✅ 合规

#### ✅ 6.2 多帧载荷 8-4095 字节

- **规范条款**: 多帧载荷 8 至 4095 字节
- **代码位置**: `isotp.h` → `#define ISOTP_MAX_PAYLOAD 4095U`；`isotp.c` FF 处理
- **当前实现**: FF 解析 12 位长度字段，校验 `payload_len > 7 && payload_len <= ISOTP_MAX_PAYLOAD`（4095）
- **结论**: ✅ 合规

#### ⚠️ 6.3 FC 帧发送（BS=0x00, STmin=1ms）

- **规范条款**: Block Size = 0x00（无限制），STmin = 1 ms
- **代码位置**: `isotp.h` → `ISOTP_FC_DEFAULT_BS = 0x00U`, `ISOTP_FC_DEFAULT_STMIN = 0x00U`
- **当前实现**: BS=0x00 ✅ 合规；**STmin=0x00（无延迟）❌ 不合规**，规范要求 STmin = 1 ms
- **差距**: STmin 应为 1ms（0x01），当前为 0ms（0x00）。这意味着接收方发送 FC 时未要求发送方在 CF 之间等待 1ms
- **修复建议**: 将 `ISOTP_FC_DEFAULT_STMIN` 修改为 `0x01U`

#### ❌ 6.4 拒绝畸形 ISO-TP 传输并恢复

- **规范条款**: 外设应拒绝畸形 ISO-TP 传输，并应在不需重新上电的情况下恢复
- **代码位置**: `isotp.c` → CF 序列号不匹配处理
- **当前实现**: CF 序列号不匹配时 `rx_ctx.state = ISOTP_RX_STATE_IDLE`，状态机恢复到空闲 ✅。但 **缺少以下畸形帧处理**:
  - FF 长度 ≤ 7 时仅丢弃（`return`），无 NRC 反馈
  - SF_DL = 0 时仅丢弃，无 NRC 反馈
  - FC 帧的 Wait/Overflow 状态未处理
  - 无超时机制处理传输中途丢失的帧
- **差距**: 畸形帧被静默丢弃，恢复到 IDLE 状态（基本合规），但缺少超时恢复机制和 NRC 反馈
- **修复建议**: (1) 添加 N_Bs/N_Cr 超时定时器，在超时时重置状态机；(2) 考虑对畸形帧发送 NRC 0x13

#### ✅ 6.5 N_As/N_Ar/N_Bs/N_Cr = 1000ms

- **规范条款**: 各层超时参数均为 1000ms
- **代码位置**: 无显式超时实现
- **当前实现**: 代码中未实现任何 ISO-TP 超时定时器。当前 MCU 仅作为接收方，多帧传输由 CCU 发起
- **差距**: 无超时机制，依赖上层应用层超时。对于当前单帧响应为主的场景影响较小，但不符合规范的严格要求
- **结论**: ⚠️ 部分合规（当前使用场景下影响有限，但规范要求明确的超时实现）

### 第 7 节：UDS 诊断服务

#### ✅ 7.1 0x10 DiagnosticSessionControl

- **规范条款**: 实现诊断会话控制服务
- **代码位置**: `can_protocol.c` → `case UDS_SID_DIAG_SESSION_CTRL`
- **当前实现**: 接收会话类型，返回肯定响应（SID+0x40 + session type echo）
- **结论**: ✅ 合规（基础实现）

#### ⚠️ 7.2 0x11 CCUReset（规范叫 CCUReset，代码叫 ECUReset）

- **规范条款**: 实现 CCU 复位服务
- **代码位置**: `can_protocol.h` → `UDS_SID_ECU_RESET = 0x11U`；`can_protocol.c` → `case UDS_SID_ECU_RESET`
- **当前实现**: 返回肯定响应后触发 `ota_trigger_request()` 执行系统复位
- **差距**: 服务名称为 ECUReset 而非 CCUReset（功能正确，命名与规范不一致）
- **修复建议**: 将 `UDS_SID_ECU_RESET` 重命名为 `UDS_SID_CCU_RESET` 以与规范保持一致
- **结论**: ⚠️ 部分合规（功能正确，命名偏差）

#### ❌ 7.3 0x22 ReadDataByIdentifier

- **规范条款**: 支持规范定义的通用 DID（0xF189, 0xF18C, 0xF18D, 0xF191, 0x2010）
- **代码位置**: `can_protocol.c` → `case UDS_SID_READ_DATA_BY_ID`
- **当前实现**: 仅支持项目专用 DID（0xF195, 0x2112, 0x2113, 0x2115, 0x2116），**未实现任何规范定义的通用 DID**
- **差距**: 缺少 0xF189（软件版本）、0xF18C（序列号）、0xF18D（Bootloader 版本）、0xF191（硬件版本）、0x2010（固件类型）
- **修复建议**: 添加通用 DID 的读取处理
- **结论**: ❌ 不合规（通用 DID 未实现）

#### ❌ 7.4 0x27 SecurityAccess

- **规范条款**: 实现 Ed25519 挑战-响应安全访问
- **代码位置**: `can_protocol.c` → `case UDS_SID_SECURITY_ACCESS`
- **当前实现**: 返回 `NRC 0x11 (serviceNotSupported)`，注释说明"APP side does not support SecurityAccess (done in bootloader safe mode)"
- **差距**: APP 侧完全不支持 SecurityAccess，所有安全操作需在 Bootloader 中完成。规范要求外设应实现此服务
- **修复建议**: 在 APP 侧实现 SecurityAccess Level 1（Ed25519 挑战-响应），或明确文档说明此服务仅在 Bootloader 模式可用
- **结论**: ❌ 不合规（APP 侧未实现）

#### ❌ 7.5 0x2E WriteDataByIdentifier

- **规范条款**: 支持写入受保护 DID（需 Level 1 安全访问）
- **代码位置**: 无
- **当前实现**: 未实现
- **差距**: 完全缺失
- **修复建议**: 实现 0x2E 服务，至少支持 DID 0x2010 的写入（需编程会话 + SecurityAccess Level 1）
- **结论**: ❌ 不合规

#### ❌ 7.6 0x31 RoutineControl

- **规范条款**: 支持例程控制（如 0xFF00 擦除例程）
- **代码位置**: 无
- **当前实现**: 未实现
- **差距**: 完全缺失。固件下载流程中的擦除步骤（步骤 4）需要此服务
- **修复建议**: 实现 0x31 服务，至少支持 RoutineID 0xFF00（擦除目标存储区域）
- **结论**: ❌ 不合规

#### ⚠️ 7.7 0x34 RequestDownload / 0x36 TransferData / 0x37 RequestTransferExit

- **规范条款**: 支持固件下载的三个 UDS 服务
- **代码位置**: `can_protocol.c` → `case UDS_SID_REQUEST_DOWNLOAD` 返回 NRC 0x11
- **当前实现**: APP 侧返回 NRC 0x11，注释说明"this is done by boot safe mode"
- **差距**: 这些服务在 Bootloader 中实现（不在审查范围内的代码文件中），APP 侧正确拒绝
- **结论**: ⚠️ 部分合规（APP 正确拒绝，但 Bootloader 实现未在本次审查范围内）

#### ⚠️ 7.8 0x3E TesterPresent

- **规范条款**: 实现测试仪在线服务
- **代码位置**: `can_protocol.c` → `case UDS_SID_TESTER_KEEPALIVE`
- **当前实现**: 返回肯定响应，功能正确
- **差距**: 名称为 `UDS_SID_TESTER_KEEPALIVE` 而非 `UDS_SID_TESTER_PRESENT`，且未处理 suppressPositiveResponse 位
- **修复建议**: 重命名为 `UDS_SID_TESTER_PRESENT`；添加 subfunction 第 7 位检查
- **结论**: ⚠️ 部分合规（功能正确，命名和 suppressPositiveResponse 处理缺失）

#### ❌ 7.9 P2 <= 50ms, P2* <= 5000ms

- **规范条款**: P2 响应时间 ≤ 50ms，P2* ≤ 5000ms
- **代码位置**: 无
- **当前实现**: 无任何响应时序监控或 NRC 0x78 发送逻辑
- **差距**: 缺少 P2 超时检测和 NRC 0x78（requestCorrectlyReceivedResponsePending）机制
- **修复建议**: 添加响应时序监控，在处理耗时操作（如 Flash 擦除、签名验证）时发送 NRC 0x78
- **结论**: ❌ 不合规

#### ❌ 7.10 suppressPositiveResponse 位处理

- **规范条款**: 0x10、0x11、0x3E 的 subfunction 第 7 位为抑制肯定响应位
- **代码位置**: `can_protocol.c` → 0x10、0x11、0x3E 处理分支
- **当前实现**: 直接发送肯定响应，未检查 subfunction 的第 7 位
- **差距**: 所有三个服务均未实现 suppressPositiveResponse 处理
- **修复建议**: 在 0x10、0x11、0x3E 处理中检查 `data[1] & 0x80`，若置位则仅执行操作不发送肯定响应
- **结论**: ❌ 不合规

#### ❌ 7.11 会话超时 5 秒

- **规范条款**: 非默认会话在 5 秒内未收到 TesterPresent 时应超时
- **代码位置**: 无
- **当前实现**: 无会话状态跟踪，无超时机制
- **差距**: 完全缺失会话管理功能
- **修复建议**: (1) 添加当前会话状态变量；(2) 添加 5 秒超时定时器；(3) 超时后返回默认会话并清除安全状态
- **结论**: ❌ 不合规

#### ❌ 7.12 会话切换清除安全状态

- **规范条款**: 进入默认会话或切换非默认会话时应清除安全解锁状态
- **代码位置**: 无
- **当前实现**: 无安全状态管理（SecurityAccess 在 APP 侧未实现）
- **差距**: 无安全状态变量，无清除逻辑
- **修复建议**: 实现 SecurityAccess 后，在会话切换时清除安全解锁标志
- **结论**: ❌ 不合规（依赖 SecurityAccess 实现）

### 第 8 节：通用 DID

#### ❌ 8.1 0xF189 软件版本

- **结论**: ❌ 不合规

## 总结

MCU 端代码在 **CAN 物理层和数据链路层** 方面完全合规，**ISO-TP 传输层** 基本功能正确但 STmin 参数和超时机制存在偏差。主要差距集中在：

1. **UDS 诊断服务覆盖不足** — 10 个必需服务中仅实现 5 个（0x10、0x11、0x22、0x27、0x3E），且 0x22 和 0x27 实现不完整
2. **通用 DID 完全缺失** — 规范定义的 5 个标准 DID 均未实现
3. **会话管理缺失** — 无会话状态跟踪、无超时机制、无 suppressPositiveResponse 处理
4. **生命周期广播缺失** — 定义了 CAN ID 但未实现任何广播逻辑

代码架构设计合理（中断驱动 FIFO + ISO-TP 状态机 + UDS 回调），为后续功能扩展提供了良好基础。建议按优先级逐步补齐规范要求的功能。
